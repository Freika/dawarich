# Expected differences between Rails and Phoenix

A Phoenix page, endpoint or email may differ from Rails only when the difference is listed here with a reason (roadmap Slice Recipe, step 4). A Track B step records a Rails behavior here when a spec cannot or should not pin it; the Track A slice that ports the surface decides the Phoenix side and closes the entry.

## A11f password work parity notes

Rails API login creates its dummy hash with `BCrypt::Password.create` without a cost option, so the effective cost is `BCrypt::Engine.cost`, not `Devise.stretches`. The installed test runtime has stretches 1 and an API dummy cost of 12. Native dummy work uses bcrypt's configured default, with the existing `log_rounds` context override; its cost must match the Rails API dummy. The actual-runtime protocol derives and checks both costs instead of assuming a literal value.

Native preflight mirrors Rails' password work for the same actor. Actors rejected before password verification for provider, settings, metadata or validation perform a verification against their stored hash and discard the result. Rails-supported `$2y$` and `$2x$` hashes stay Rails-owned; native preflight changes only the comparison prefix to `$2b$` and discards the result, preserving work at their stored cost without admitting them for native authentication. `$2a$` actors retain the existing supported comparison. Supported wrong-password actors and rejected actors therefore both perform native[c] + Rails[c] at their stored cost c. Admitted missing/deleted actors perform one default-cost native dummy operation before Rails' own dummy comparison. Blank stored hashes perform two native dummy operations because Devise skips comparison for a blank hash.

The deterministic controls trace native work and actual Rails fallback for supported and rejected cost-4 actors, default-cost actors, missing/deleted actors and blank hashes. They assert native plus Rails work equals twice the actual Rails-only pattern for the same actor or miss, including low-cost `$2a$`, `$2y$` and `$2x$` controls, unchanged actor rows, original replay bytes and the public refusal contract. Blank hashes retain the controller-required compensation of two native default-cost operations with zero Rails operations; their baseline is the Rails miss pattern. Stored-cost variation between an actor and a missing email is inherited from Rails; no stricter stored-cost admission policy or new expected difference is introduced.

Passwords containing a NUL byte hand back before native actor lookup or bcrypt, with the original request bytes. Rails bcrypt raises for the embedded-NUL controls; native performs zero comparison work and cannot authenticate a correct prefix. OTP challenge codes already exclude NUL; API two-factor management also hands back NUL-bearing password/code inputs before lookup or writes. These are source-owned inputs, not a new expected difference.

Emails containing any non-ASCII byte also hand back before native lookup or password work. Rails alone selects the actor using its Ruby Unicode normalization tables; native does not introduce a second Unicode-version-dependent actor selection. Actor-selection and known/missing/deleted wrong-password controls pin original-byte replay and zero native work for these inputs.

API OTP refusal preflight mirrors Rails' read-only TOTP-then-backup verification, including provider/settings/password/metadata rejection, the enabled flag, legacy backup hash prefixes and secret states. It scans backups at their stored costs and stops at the same match or invalid-hash boundary; missing/blank secrets skip TOTP but still scan backups, unreadable secrets preserve Rails' exception ownership, and locked actors scan backups without TOTP. Unsupported results are discarded before any native save or consumed marker. Deterministic native traces and actual Rails requests compare the same work pattern, including successful codes on actors that must replay. Missing encryption admission settings do not skip read-only work when Rails can still decrypt the stored secret. Successful native writes retain the existing separate-save/cache/reset order.

Password hashes accepted by Rails' structural grammar but not computable by bcrypt use the same two default-cost native dummy operations as a blank stored password. This includes costs 00–03 and 32–99 and unsupported subtypes. Rails still owns the refusal and performs no adaptive comparison for those hashes. Structurally invalid password hashes replay with zero native crypto, preserving Rails' `InvalidHash` exception. Controls exercise all four computable subtypes at costs 00–03, both out-of-range cost boundaries, unsupported subtypes and malformed hashes; native authentication never admits these states. OTP backup preflight skips uncomputable hashes without dummy work and preserves the source scan boundary.

Signed challenge user IDs outside PostgreSQL's positive bigint range replay before native cache or actor lookup. Rails owns the usual invalid-challenge response for its unboundable actor lookup; the maximum valid bigint remains admitted at token verification.
