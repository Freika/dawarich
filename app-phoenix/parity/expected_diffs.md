# Expected differences between Rails and Phoenix

A Phoenix page, endpoint or email may differ from Rails only when the difference is listed here with a reason (roadmap Slice Recipe, step 4). A Track B step records a Rails behavior here when a spec cannot or should not pin it; the Track A slice that ports the surface decides the Phoenix side and closes the entry.

| ID | Surface | Rails today | Phoenix | Owner | Status |
|---|---|---|---|---|---|
| ED-001 | Throttled browser form posts: `POST /users/sign_in`, `POST /users`, `POST /users/otp_challenge`, `POST /auth/account_link/challenge`, `POST /s/:id/unlock` | rack-attack's `Rack::Attack.throttled_responder` (`config/initializers/rack_attack.rb`) answers every throttle, browser forms included, with HTTP 429, `Content-Type: application/json`, `Cache-Control: no-store`, `Retry-After` (seconds to the end of the window) and the body `{"error":"rate_limit_exceeded","message":"API rate limit exceeded. Please wait before making more requests.","upgrade_url":"<MANAGER_URL>/pricing"}`; the browser shows the JSON instead of the form. Since `fix/self-hosted-no-throttles` self-hosted instances throttle only the last two paths; Cloud throttles all five. Not pinned by a spec: reaching a throttle spends a budget every other spec shares. | Decided by A11 (sign-in, sign-up, OTP, account link) and A9 (shared-link unlock): reproduce the JSON 429, or render the form with an error and record the reason here. | A11 | open |
| ED-002 | Release migrator (ADR 0015, live from A12): a database older than 1.0.0, i.e. its `schema_migrations` lacks a migration of a state up to `0.37.2` | `db:migrate` upgrades a database from any earlier release | Refused before the lease and before any change: `refused: this database has not reached Dawarich <release>, and this image upgrades only from 1.0.0; start the Dawarich 1.15.2 image once so Rails upgrades it, then start this image`. `<release>` is the oldest release whose migrations the database lacks. `1.15.2` is `@last_rails_release` in `mix dawarich.release_migrate`; A12 bumps it to the last Rails release, checks that this release upgrades a pre-1.0.0 database without crashing, and prints the same text from its release command. The message names one release, not "any image from 1.0.0": 1.3.2 and 1.7.0–1.7.2 crash on upgrades from 1.0.0 or earlier after the floor versions commit and before `rake data:migrate` (`db/release_snapshots/README.md`). The upgrade note of the release that removes Rails names that release (ADR 0015, amendment "upgrades supported from 1.0.0") | C2 | closed |
| ED-003 | Release migrator: a non-empty `schema_migrations` that holds no Dawarich floor version (another application's database) | `db:migrate` ignores the foreign versions as `NO FILE` and runs every Dawarich migration into that database | Refused before the lease and before any change: `refused: schema_migrations holds <count> versions and none of them is a Dawarich migration; check DATABASE_NAME`. Checked before the floor, so such a database never gets the 1.0.0 remedy. Remedy: point `DATABASE_NAME` at the Dawarich database | C2 | closed |
| ED-004 | Release migrator: `schema_migrations` exists but is empty | `db:migrate` runs every migration from the first | Treated like a missing ledger: the baseline builds `db/schema.rb` as Rails' `db:schema:load` would on that database (`fresh:empty`). With an application table present, the baseline stops at it and changes nothing. Migrations before 1.0.0 have no Ecto port | C2 | closed |
| ED-005 | Release migrator: a second run at the same time | Fails at once with `ConcurrentMigrationError` (session advisory lock) | Waits up to 15 minutes for the lease row, then refuses and names the holder: `refused: another migrator holds the lease (<holder>)`. Session advisory locks are unsafe behind PgBouncer | C2 | closed |
| ED-006 | Release migrator: `20260816120000`, `20260818201239` | `SET lock_timeout = 0` / `RESET lock_timeout` on the session before `CREATE INDEX CONCURRENTLY` | No session `SET`; the migration stops with a clear message when the role or database sets a non-zero `lock_timeout`. A session `SET` leaks to other clients through PgBouncer | C2 | closed |
| ED-007 | Release migrator: session time zone | `SET SESSION timezone TO 'UTC'` | The `timezone` startup parameter: the same effect without a session `SET`. When the session still is not UTC (a pooler that drops the parameter), the migrator refuses before any change: `refused: session time zone is <value>, not UTC` | C2 | closed |
| ED-008 | Release migrator: jobs a migration enqueues | Reach Sidekiq when the migration runs; a migration that enqueues and then fails outside a transaction leaves its job queued | Recorded in `phoenix.release_migration_jobs` with the version's ledger row; a failed version records none. Sidekiq is gone at A12, and no job is lost or duplicated. Nothing reads the outbox yet: C3 and A12 add the consumer | C2 | closed |
| ED-009 | Release migrator: Rails tables outside `public` (another `search_path` or schema) | Migrated wherever the search path points | Refused with the schemas named: the ledger and every ported statement assume `public` | C2 | closed |
| ED-010 | Release migrator: leftover tables but no `schema_migrations` | Overwritten by `db/schema.rb` (`force: :cascade`) | The baseline stops at the first existing table and changes nothing: data is never dropped implicitly | C2 | closed |
| ED-011 | Release migrator: ledger versions without a migration file | Ignored (`NO FILE`) | Versions this image does not know are refused: `refused: newer than this image (<versions>)`. Floor, known removed and schema.rb define versions are excepted. Remedy: start the Dawarich image that created them, or restore the pre-upgrade backup. A newer or release-candidate database must not be half-understood | C2 | closed |
| ED-012 | Release migrator: a Rails migrator running at the same time | `db:migrate` also runs while another process migrates with advisory locks disabled | Refused while Rails' migrator advisory lock is held (self-hosted), at start and again in every version's ledger transaction. On Cloud (`DATABASE_ADVISORY_LOCKS=false`) the deploy guarantees no Rails migrator runs. Two migrators must never interleave | C2 | closed |
| ED-013 | Release migrator: `ar_internal_metadata` | `environment` and `schema_sha1` written on every run | Not written or updated: only Rails reads it | C2 | closed |
| ED-014 | Release migrator: a lost connection inside a lock retry, `20260816150000` (1.13.1) and `20260714090000` (1.10.1) | Retries on `ActiveRecord::LockWaitTimeout` and `ActiveRecord::QueryAborted`, which also covers `ConnectionFailed` and `AdapterTimeout`. After the last attempt 1.13.1 logs and continues (the column is left to `DataMigrations::AddPointDimensionColumnsJob`), and 1.10.1 hands off to `DataMigrations::DropLegacyLatLonJob` | Retries only on Postgres `lock_not_available` (55P03) and `query_canceled` (57014). A lost connection (`DBConnection.ConnectionError`) fails the version, and the next start resumes at it. Both steps are idempotent (`IF NOT EXISTS` / `IF EXISTS`, and a backfill that re-filters) | C2 | closed |
| ED-015 | Release migrator: a lost connection inside the rescued job queries of `20260125100000` (1.0.2) and `20260206202634` (1.1.0) | `rescue StandardError` also swallows `ConnectionFailed` / `ConnectionNotEstablished` from the `SELECT id FROM users …`, `SELECT id FROM imports …` and `SELECT COUNT(*) …` queries: the version is recorded with no jobs, so they are never enqueued for that database | `rescue_sql(…, :any, …)` rescues only `Postgrex.Error`. A lost connection fails the version, and the next start re-runs it: 1.1.0 then records the `Tracks::DeduplicationJob`s Rails skipped. 1.0.2 ends as Rails' normal run does, with no jobs, because current Rails enqueues nothing there (the user half names a deleted job class, and the import query fails on the integer `source` column, a `Postgrex.Error` the port rescues) | C2 | closed |
| ED-016 | Release migrator: `Flipper.enable(:poster_ordering)` in `20260730200000` (1.11.0) | Flipper's `add` inserts the feature row in a savepoint and rescues `RecordNotUnique`, so a feature row committed by another process at the same moment is tolerated. `clear` deletes the gates it loaded, by id | One statement group in the version's transaction: the feature row is inserted `WHERE NOT EXISTS`, and the gates are deleted by `feature_key`. A concurrent insert of the same row fails the version with 23505, and the next start resumes at it; a gate committed by another process between Rails' load and delete would be deleted here and kept by Rails. The risk is concurrency, not order: Phoenix's port of `FeatureFlags.apply_defaults!` runs before the migrator, sequentially in the same release process, and never at the same time as it (ED-020) | C2 | closed |
| ED-017 | Release migrator: `db/data` migrations and `data_migrations` | `docker/web-entrypoint.sh` runs `rake data:migrate` on every start, which runs every `db/data` migration missing from `data_migrations` (Cloud's release step runs only `db:migrate`) | Runs no `db/data` migration and never writes `data_migrations`. All 27 predate the 1.0.0 floor, so a database the entrypoint started at or past the floor has run them. The exception: a Rails upgrade from 1.0.0 or earlier that crashed in 1.3.2 or 1.7.0–1.7.2 after the floor versions committed and before `rake data:migrate`, followed directly by this image. The floor check then passes and those data migrations never run, which is why ED-002 names one release that upgrades cleanly | C2 | closed |
| ED-018 | Release migrator: `SKIP_POINT_DIMENSION_BACKFILL` holding bytes that are not valid UTF-8 | `ENV[…].blank?` raises `ArgumentError` and the version fails | The value counts as set, and the backfill job is skipped. Not a real configuration | C2 | closed |
| ED-019 | Release migrator: the seven synchronous app-code calls (`Achievements::LoadRegions` ×2, `Achievements::MigrateExplorationState`, `DataMigrations::DedupeTracksForUniqueIndexJob`, `DataMigrations::BackfillPlacesUserIdJob`, `Geocoding::SeedFromEnv`, `InstanceSettings::Backfill`) | Run inside the migration | The version stops with `UnportedEffect` behind a no-work condition at least as broad as Rails'. On a populated database most of them fire: 1.13.1's on every self-hosted database with a user, 1.15.0's on every database with a user, 1.7.6's on every database with duplicate tracks. So no populated database gets past 1.15.0 before C3 replaces each `unported!` with the port of its effect, which it must do before A12 | C3 | open |
| ED-020 | Boot-time data writes | `FeatureFlags.apply_defaults!` writes default Flipper features on every start: the release step boots the app, which runs it, before `db:migrate` migrates, and every web boot runs it again | Not part of the migrator. Phoenix's release step runs its port of the defaults (when the Flipper tables exist) before the migrator, sequentially in the same process, reproducing the order the harness proves; web boot runs it again, as Rails does. The two never run concurrently (ED-016) | A12 | open |
